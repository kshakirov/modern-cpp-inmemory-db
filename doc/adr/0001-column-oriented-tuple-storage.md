# ADR 0001: Выбор структуры слоя хранения данных (Column-Oriented SoA через std::tuple)

## Дата
2026-07-26

## Статус
Принято

## Контекст
Передо мной стоит задача спроектировать in-memory движок реляционной алгебры, способный эффективно обрабатывать тяжелые аналитические выборки данных и минимизировать накладные расходы в рантайме.

Существуют два классических подхода к размещению реляционных кортежей в памяти:
1. **AoS (Array of Structures / Построчный подход)**: Единый массив структур, где поля одной строки лежат последовательно.
2. **SoA (Structure of Arrays / Колоночный подход)**: Раздельные массивы для каждой колонки, где данные одного типа лежат непрерывно.

Построчный подход (AoS) ухудшает локальность кэша процессора при аналитических запросах (агрегации, фильтрация по одной колонке), забивая кэш-линии (L1/L2) ненужными соседними данными. Также он делает невозможной автоматическую SIMD-векторизацию и усложняет алгоритмы статистического сжатия колонок (RLE, Dictionary Encoding).

Динамическое стирание типов (через ООП-интерфейсы `BaseColumn` или рантайм-карты по строковым ключам а-ля `std::unordered_map`) приводит к постоянным промахам по кэшу из-за указателей и накладным расходам на вызов виртуальных функций/хэш-функций, что противоречит принципу нулевых накладных расходов Бьёрна Страуструпа.

## Решение
Я принимаю решение реализовать слой хранения на основе **колоночного подхода (SoA)** с жесткой compile-time типизацией метаданных.

1. **Физическая структура**: Таблица/Реляция в памяти представляется в виде гетерогенного статического кортежа `std::tuple`, элементами которого являются гомогенные динамические векторы `std::vector<T>` для каждой конкретной колонки.
2. **Compile-Time метаданные**: Строковые имена колонок передаются как нетиповые параметры шаблонов (Non-Type Template Parameters / NTTP) благодаря возможностям стандарта C++20. 
3. **Мета-слой доступа**: Преобразование строкового имени колонки (например, `"age"`) в целочисленный индекс элемента в `std::tuple` (например, `2`) полностью делегируется компилятору (GCC 15) на этапе сборки. В рантайме строковые литералы отсутствуют, а вызов транслируется в прямое смещение по памяти через `std::get<I>`.

## Последствия

### Положительные:
* **Симбиоз с железом**: Идеальная кэш-локальность («Танго и Кэш») при сканировании конкретных колонок. Компилятор получает возможность генерировать SIMD-инструкции для векторизации циклов.
* **Zero-Cost Abstractions**: Полный отказ от ООП-полиморфизма, динамических аллокаций под метаданные и рантайм-поиска по строкам. Ошибки в схеме данных выявляются на этапе компиляции.
* **Потенциал сжатия**: Плотные массивы однородных данных готовы к внедрению легковесного сжатия.

### Отрицательные / Риски:
* **Цена модификаций**: Добавление или удаление одной строки (Tuple-at-a-time insertion) становится дорогой операцией, требующей аллокаций во всех векторах кортежа независимо. Однако, в рамках статической природы реляций в данном проекте этот минус не является критическим.
* **Сложность метапрограммирования**: Написание DSL-оберток над `std::tuple` и обработка вариадических шаблонов усложняют чтение самого кода движка разработчиком.
