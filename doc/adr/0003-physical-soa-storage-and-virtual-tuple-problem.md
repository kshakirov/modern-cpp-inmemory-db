# ADR 0003: Проектирование физического слоя хранения (SoA) и открытая проблема виртуальной сборки кортежей

## Дата
2026-07-26

## Статус
В процессе обсуждения (Открытая проблема)

## Контекст
В соответствии с ADR 0001, я перехожу к наполнению структуры `LatticeStorage` реальным физическим телом. В качестве первой аппроксимации выбрана фиксированная схема таблицы `Users`, состоящая из трех доменов (типов):
* `id` (уникальный идентификатор): `std::int64_t`
* `name` (имя пользователя): `std::string`
* `age` (возраст): `std::int32_t`

Для обеспечения максимальной кэш-локальности («Танго и Кэш») и создания условий для SIMD-векторизации компилятором GCC 15, я материализую данные по колоночному принципу (Structure of Arrays - SoA). Физическим контейнером внутри `LatticeStorage` становится гетерогенный монолитный кортеж `std::tuple`, элементами которого являются гомогенные динамические векторы `std::vector<T>` для каждой соответствующей колонки.

## Постановка проблемы
Колоночная организация данных (SoA) создает фундаментальный разрыв между физической реальностью железа и логическим мышлением человека (а также требованиями реляционной алгебры):
1. **Железо** оперирует независимыми, параллельными реками байт (`id_vector`, `name_vector`, `age_vector`). Монолитной структуры "Строка" или "Пользователь" в натуре в оперативной памяти **не существует**. Данные одного логического кортежа разорваны и разнесены по разным адресам DRAM.
2. **Человек** (и интерфейсы вывода, такие как чистая свободная функция `dump`) мыслит горизонтальными сущностями — строками. Чтобы напечатать таблицу или передать результат фильтрации дальше по конвейеру, движок обязан как-то «собрать» эти разрозненные поля воедино.

### Возникает критическая инженерная дилемма:
Как осуществлять транзит и сборку данных через чистые функции реляционных операторов, не разрушая преимуществ SoA-хранения? 

*   **Наивный путь создания временных объектов**: Сборка полноценной структуры `User` на каждой итерации цикла приведет к тотальному копированию памяти (особенно тяжелых аллоцированных в куче `std::string`), что мгновенно нивелирует весь выигрыш от кэш-локальности колонок. Процессор захлебнется в «мусорных» рантайм-операциях.
*   **Путь жонглирования указателями/ссылками**: Создание временных кортежей ссылок (`std::tuple<const int64_t&, const std::string&, ...>`) усложняет систему типов, создает риски для времени жизни объектов (Lifetime / Ownership по Харперу) и может породить Pointer Chasing (разрушение кэша из-за разыменования указателей).

## Решение
*Раздел временно пуст. Ведется самостоятельное исследование оптимального абстрактного идентификатора позиции элемента (начиная от Кнутовских концепций индексации и заканчивая ленивыми корутинами) для построения Zero-Cost моста между колоночной памятью и строковым логическим конвейером.*

## Последствия
*Будут сформулированы после фиксации и верификации выбранного инженерного маневрa.*
